# x-plan

## 三種東西，各管一件事

都平躺在 `<workspace>/worktree/<issue-slug>/`，與各 repo 的 worktree **同層**，不放進任何一個 repo
裡面——放進去的話 `git worktree remove` 與重建都會把它清掉，而它要活得比任何一個 repo 的 worktree 久。

| 哪一種 | 裝什麼 | 什麼時候變 |
|---|---|---|
| 判準（出處可能不只一處，也未必是檔案） | **判準**——規格說什麼才算對。實際出處逐列寫在頭的〈判準出處〉 | 規格被改動時。本 skill 不寫這些 |
| `PLAN.md` | **計畫與日誌**——要做什麼、做了什麼 | 每個 session |
| 事實／量測 | **事實**——這台機器、這份 code 實際是什麼 | 每量一次多一筆 |

判準與事實是兩種東西，混在一起會壞掉：判準跨環境成立、規格改才變；事實綁在被量的那個對象上，
換一台機器、換一個版本就不同。「回應要在 500 ms 內」是判準；「這台上實測 P95 是 820 ms」是事實。
同一句話不會兩者都是。

事實**預設寫在 `PLAN.md` 的〈事實〉節**。外拆成獨立檔的條件只有一個：**另一張 issue 要引用它**。
拆不拆跟存活無關——issue folder 被清理時整個目錄一起走，要保留哪些由清理流程當下逐一問，
不要預先把東西搬去別的地方，那只會製造兩份真相。

## `PLAN.md` 的骨架

```markdown
# <issue 編號>：<標題>

## 頭
- 一句話：<要讓什麼變成什麼，不寫背景>
- 範圍：做 <…>；**不做** <…，各一句理由>；**先出的缺口** <症狀／對端／實機，各附數字與理由；沒有寫「無」>
- 上游：<repo> ← <依賴的形式：branch / tag / 版號 / PR 編號>；本地當前 base <SHA>
- 判準出處：
  - `<來源：檔名／issue URL／prompt 日期>` — <它回答什麼> — <版本：SHA 或讀取日期>
- 切片順序：垂直 / 契約先行 / 風險先行 — <一句理由>
- 進度：N 項，M 完成｜最後更新 <日期>，見日誌 <該則標題>

## 項目
<索引表 + 每項一個小節，見下>

## 事實
<就地改寫。每筆：量到什麼、在哪個環境、用什麼指令、對端當時的設定、這一層驗不到什麼。有要修的執行期失敗時，先列症狀清單（見〈事實怎麼記〉）>

## 未決事項（尚未定案，勿當結論）
<每條標「等誰」>

## 日誌
## <YYYY-MM-DD>：<這則在做什麼>
...往檔尾追加
```

**頭要在 60 行內讀得完。** 項目那一節不算在內——它自己一節，完成的項目留在原地不刪（狀態欄看得出來）。

### 〈判準出處〉是清單

判準可能來自規格節錄、PRD、另一支流程產出的檔，也可能同時有好幾份（規格加上 PM 口頭定案的
紀錄）。每列寫「來源 — 它回答什麼 — 版本」，版本那格是之後判斷「我讀的跟現在的是不是同一份」的
唯一依據。

**第一次寫 `PLAN.md`、清單還是空的時候**：`ls` 這個 issue folder，除了 `PLAN.md` 之外的每個
`.md` 都是候選，逐一讀開頭看它回答什麼，填進清單。今天會出現的是 `GROUNDWORK.md`，但不要只找
這個名字——它只是讓第一次執行有個看得到的落點，不是依賴哪支流程先跑過；判準的產出方式會變，
`ls` 找得到新的，寫死檔名找不到。

**一個候選都沒有時判準不會消失，它只是不在檔案裡。** 使用者的 prompt、issue body、既有 code
都是合法出處，照樣一列一列寫進〈判準出處〉：

| 這一輪的判準來自 | 版本那格填 |
|---|---|
| issue body 原文 | issue URL + 讀取日期（PM 隨時會改，日期是之後比對的唯一依據） |
| 使用者這一輪的口頭指定 | 日期 |
| 依既有 code 推的 | `file:line` |

三種都寫不出來才寫「無判準」，並在〈未決事項〉標「等誰補規格」。**不要把判準寫進〈事實〉**——
那一節每筆都要有指令輸出、`file:line` 或規格原文當出處，一句 prompt 三種都不是，寫進去之後
下一個人分不出哪幾行是要求、哪幾行是量到的。

## 先畫依賴圖

拆項目之前先把「誰依賴誰」畫成一張圖（ASCII，放進〈頭〉或〈事實〉），實作順序由下往上：
被依賴的先做。跨 repo 的邊要標依賴形式（tag / 版號 / branch），那條邊就是〈上游〉欄的內容。
沒畫圖就排順序，排出來的是「我想先做哪個」；索引表的〈依賴〉欄也只能靠印象填。

## 項目

分兩層寫：一張索引表看全局，每項一個小節放細節。

**索引表**——`#` / `狀態` / `做什麼` / `依賴` 四欄，一項一列：

| # | 狀態 | 做什麼 | 依賴 |
|---|---|---|---|
| 1 | ⬜ / 🔨 / ✅ / ❌不做 | 動詞開頭一句話 | 項目編號或「無」 |

**每項的小節**——標題是 `### <#> <狀態> <做什麼那句>`，內容三個項目符號，名稱與順序固定：

```markdown
### 3 ⬜ manager 實作 `ListVolumes` 的 System 那半

- **完成判準**：完成時什麼會成立，指得著某個輸出說符合或不符合。
- **怎麼驗**：環境 + 跑了什麼 + 對端當時的設定。**驗不到**：這一層驗不到什麼。
- **動到的檔**（所屬子系統）：
  - `path/one.go`
  - `path/two.go`
```

〈狀態〉在索引表與小節標題各一份，那是刻意的——單獨讀一個小節時要知道它做完了沒。
〈依賴〉只在索引表，小節不重複：它的用途是排順序，那要一次看到全部項目才判斷得了。

**分界綁欄位，不綁那一項的內容量。** `#` / `狀態` / `做什麼` / `依賴` 是一格一個值，留在表格；
`完成判準` / `怎麼驗` / `動到的檔` 照本 skill 的規定都是多句散文（〈怎麼驗〉是四段、〈完成判準〉
是一個完整斷言），而 markdown 表格的一列在原始檔裡就是一行、不能斷行。把散文寫進格子，
產出的是幾百字元一行的來源檔：編輯器不對齊表格時，內容會掉到跟表頭對不上的續行上，讀不了。

不要按「這一項比較簡略」逐項挑形狀。那樣讀者要先判斷這一項是哪種形狀，才知道往右看還是往下看，
〈收尾檢查〉那兩條（小節三個項目符號都在、每筆驗證寫了四件）也就不能用眼睛掃過去。而且「簡略」
沒有判準——照規定寫的項目不可能簡略，真的簡略的多半是那三個項目符號沒寫齊。

**〈做什麼〉是一句話，括號裡的清單搬進小節。** 索引表那格出現型別清單、檔名列舉、參數說明時，
它已經不是一句話了——那些屬於〈完成判準〉或〈動到的檔〉。索引表每列在 80 個顯示欄寬內
（中文字算兩欄）是這條的外顯檢查。

**完成判準是最容易漏的一項。** 沒有它，「這項做完了沒」只能靠印象，接手的人
與下一個 session 的自己都答不出來。寫不出完成判準，代表這一項的範圍還沒收斂，先別開始做。

**規格沒寫到的輸入。** 項目拆完、交給使用者看之前，對著〈判準出處〉列出規格隱含、但沒有任何
一項的〈怎麼驗〉會碰到的輸入或條件——空值、邊界值、重複請求、對端不在線這一類——最多五條，
最可能出事的排前面，每條一句：什麼輸入、一個合理的人預期什麼行為。每條要嘛寫進負責那段 code 的
項目的〈怎麼驗〉——寫出餵這個輸入的 test 名稱或指令、以及預期輸出，只寫「也要擋」不算——要嘛
寫進頭的〈範圍〉的「不做」，理由寫這個輸入會造成什麼結果、為什麼可以接受（「規格沒寫」不是理由：
規格沒提到一個輸入，不等於那個輸入可以讓程式壞掉）。這份清單連同落點記在項目給使用者看過的那則
日誌；之後重拆或新增項目，在那次給使用者看的那則再列一次。一條都列不出來時寫「無」與理由。

**驗收對照。** 項目拆完、交給使用者看之前，判準檔的每條驗收（`GROUNDWORK.md` §4、issue 的
Acceptance Criteria）逐條對到一項的〈怎麼驗〉：寫出 test 名稱或指令，以及預期輸出。驗收以某個
狀態為條件時（例如「離線的節點可以從叢集刪除」），畫一張表：列是計畫裡會被判成那個狀態的
每一種情況（例如「斷線」「重開機中」都算離線，來源是各項的〈怎麼驗〉與判定規則；〈怎麼驗〉裡分開列出的情況各佔一列，不得併成一列），欄是以那個
狀態為條件的每一條驗收。每一格要一個 test，驗的是**那條驗收講的行為**（刪除成功），不是「會不會
被判成那個狀態」；做不到的格子寫進頭的〈範圍〉的「不做」，點名是哪一格、會造成什麼結果。只寫
「驗不到」不算；「那段 code 本單沒改」也不算，因為判定規則決定了哪些情況會走進那段 code。之後
判定那個狀態的規則被改動、確認或重述時（例如什麼算離線），在那則日誌重畫這張表，規則新涵蓋的情況各加一列。

**要再拆的四個訊號**，任一成立就拆，四個都是看得見的形狀：

- 動到超過 5 個檔
- 動到兩個以上獨立子系統（跨 repo 算，同 repo 的 handler 與 storage 也算）
- 〈完成判準〉那一項寫不進三個句子
- 〈做什麼〉那句裡有「和」「並」「順便」——那是兩項被寫進同一項裡

### 診斷型的項目

〈事實〉有症狀清單時（見〈事實怎麼記〉），清單上每個症狀至少要被一項非 `CP` 的〈完成判準〉點名，點名症狀的
項目就是診斷型；「修 bug」這類說法不是判準，標題寫成調參數、加 log 都一樣。診斷型項目的小節在三個
固定項目符號**之前**多一段診斷，順序固定：**問題 → 根因（各候選附證據，或標「未驗:」）→ 候選修法與
各自的 side effect**。診斷在前，因為候選修法的取捨要靠根因才判斷得了；把修法寫在根因前面，等於先選了
答案再找理由。診斷段落不重寫驗證方式與動到哪些檔——那兩件就是後面的〈怎麼驗〉與〈動到的檔〉。

診斷段裡每個被採用的候選修法，實作它的那一項也要在〈完成判準〉點名它要修的症狀，也是診斷型。一個
症狀採用了幾個修法，就有幾項要點名它——只要有一項不點名，那一項就能只寫「改了什麼」直接 ✅。
〈完成判準〉或註解以症狀清單上某條為改動理由的項目，也是診斷型。
使用者或其他人指定的修法（口頭、issue、review comment 都算），一定要出現在某個診斷段的候選修法裡，旁邊寫是誰在哪裡指定的。修法不是判準，不寫進〈判準出處〉。

「根因」列至少兩個候選原因，其中一個要是「它成立時，打算採用的修法無效」的那種。每筆引用的證據旁邊
填一格「若 <另一個候選> 成立，這裡會看到 ___」；每個候選都填不出不同的東西（例如只是重述症狀的失敗
訊息），根因標「未驗:」，候選修法之間怎麼取捨照 x-user-rules〈機制句當理由要有證據〉。同一個條件跑
3 次都重現的確定性 bug，可以只列一個候選，前面「修法無效的候選」那條也一併免除。

修法已經由使用者或其他人指定、而根因是「未驗:」時，動手前先回報給使用者：哪個候選原因成立時
這個修法無效、要量什麼才分得開。日誌記一則：回報了什麼、使用者怎麼決定。

這類項目的〈完成判準〉寫成症狀量到的結果，不寫「改了什麼」：在修前失敗率的同一個條件下，修後跑
N 次、失敗 0 次，而且「修前失敗率 × N ≥ 3」——不到 3，修後的 0 次失敗和修前分不出來（修前失敗率
1/7 時要 21 次；確定性 bug 是 3 次）。修前的分母和修後的 N，都只算那支測試或那個重現指令實際執行到
的次數；修後的失敗數算那支測試或那個指令的任何失敗，不比對訊息原文——修法常會改掉訊息（例如
`over 5s` 變成 `over 30s`），訊息原文只用來認出修前的症狀。沒達到就維持 🔨，在〈未決事項〉寫
「等誰：CI（再跑 N 次）／使用者 — 還要量什麼」；要先出貨，寫進頭的〈範圍〉〈先出的缺口〉：修前修後的
數字、根因是否「未驗:」，由使用者判斷夠不夠。

### checkpoint

每 2–3 項插一個 checkpoint，內容是「到這裡為止整條路走得通」，不是「這幾項做完了」。

它在索引表佔一列：`#` 欄寫 `CP1` / `CP2`（依序編號，不要都寫 `CP`——一份計畫有好幾個
checkpoint，不編號就對不到下面是哪個小節），〈做什麼〉寫這一段要證明走得通的是哪一條路。
小節只有〈完成判準〉一項，寫要攤出來的實物是什麼——checkpoint 沒有〈怎麼驗〉與〈動到的檔〉，
攤出實物本身就是驗證。**checkpoint 要停下來給使用者看**，帶上那些實物
（diff、對照表、指令輸出），不是只報進度。設計上的取捨如果一路到收尾才攤開，往返成本比
中途停一次高得多。

〈事實〉的症狀清單非空時，清單上每個症狀至少要被一個 checkpoint 的〈完成判準〉點名，攤出的實物
就是那條症狀底下的修前修後數字；還沒達到「修前失敗率 × N ≥ 3」的，在那個 checkpoint 寫「未達門檻」，
不算涵蓋，這個 checkpoint 維持 🔨。到最後一個 checkpoint 都沒涵蓋的，寫進頭的〈範圍〉〈先出的缺口〉，
內容同〈診斷型的項目〉最後一段。
只寫「這幾項做完了」的判準，打勾時對沒點名的症狀什麼都沒證明，讀的人卻會以為整張 issue 都過了。

## 切片順序

三種，選一種寫進頭：

- **垂直切片（預設）** — 一次做完一條**使用者看得到的能力**，而不是先改完所有 schema 再改所有
  服務。一片可以跨好幾層、好幾個 repo，那仍然是一件事；「一件事」指的是能力不是層。
- **契約先行（跨 repo 的預設）** — 先定契約、合併、發版，下游再 repoint 到新版重新產碼。切片是
  「契約 → 各消費端並行 → 串接」。哪個 repo 先合、下游何時 repoint，寫進頭的〈上游〉。
- **風險先行** — 最不確定的那片先做（機制沒驗過、實機行為不明、外部規格沒查清）。它失敗的話
  後面幾片是白做的。

多個 session 或多支 agent 同時進行時：獨立的切片、已實作功能的測試、文件可以平行；schema 變更、
共用狀態、依賴鏈必須序列；共用一份契約的兩端要先把契約定完才分頭做，否則兩邊各對著自己想像的
形狀寫。

## 每一片的循環

實作 → 驗證 → 記進日誌 → 下一片。不要累積多片再一起驗。

**commit 不在這個循環裡**——什麼時候 commit、訊息怎麼寫，不歸這份產物管，照既有的 commit 規範
與使用者的指示。那一則日誌裡沒有 commit 可寫時就寫「未 commit」，不要留白——留白讀起來像忘了記。

一片之內只做一件事。順手改的不算——真的看到值得改的，寫進日誌那則的末尾，不動手。
每一片結束時專案要建得起來、既有測試要過。

## 驗證怎麼記

每筆驗證記四件事（讀了服務 log 的那筆另加第五件：反向篩選，見本節末），缺一件那筆就不算數：**跑在哪個環境、跑了什麼、對端當時的設定是什麼、
這一層驗不到什麼**。

環境不是固定的三層清單，把實際跑的那個寫出來就好——本機 build/測試、模擬環境（QEMU / loopback /
VM / 容器）、跨 repo 串接、實機、外部契約探測（`busctl`、`nmcli`、`sysfs`）、別人給的現場證據。
每一種都有它蓋不到的東西，而**「這一層驗不到什麼」才是這一欄的重點**：單元測試全綠而實機才炸的
那一類，差別就在假物件對「狀態現在是什麼」回了固定值，把真實世界的競賽從測試裡刪掉。

**對端當時的設定是什麼**——先看開工前的判準檔有沒有對端依賴表。有，就逐列對上：表上
每一列，這筆驗證要說出那個對端當時被設成什麼，或明寫「這筆沒有涵蓋這個對端」。沒有那
張表（或那張表是空的），這一欄寫「未盤點對端」——不是留白，因為留白讀起來像沒有對端。

這一欄要有出處：說對端「已經設好了」要指得出一條本 session 跑過的指令與輸出，或一份
註明來源與日期的設定輸出。指不出來就只能寫「未確認對端設定」——那是合格的答案，
「已設好」不是。

答的必須是對端被設成什麼，不是環境長什麼樣：「接了一般的 switch，兩個 port 沒設 LAG」
合格；「實機驗證」「一般環境」「在 dev1 上」都不合格，它們回答的是別的問題。而「沒設時
實際會怎樣」如果這筆量到了，那是〈事實〉的內容，不是這一欄。

表上那一列的「對端要設什麼」是「未查」時，這一欄仍要寫對端當時的設定，並在〈驗不到
什麼〉寫「對端要求未查，無法判斷這次的對端設定是否滿足它」——否則那個未查會在下游
消失，而它正是還沒查完的那件事。

這一欄存在的理由是下一欄（「這一層驗不到什麼」）要人自己想出來，而想不到正是它會漏的時候。
對端表把它從「想起來」變成「對得上／對不上」。

實機驗證可以延後出貨，但要在頭的〈範圍〉〈先出的缺口〉裡指名**哪一項還沒有實機驗證、以及為什麼可以先出**。

實機驗證讀了服務 log 的那筆，除了 grep 自己預期的行，還要記一次**反向篩選**：限定那個 unit 與
這次操作的時間窗，排除服務自己 logger 的正常等級（例如 `grep -vE 'level=(INFO|DEBUG)'`），
剩下的行數與內容寫進那筆，0 行就寫 0 行。grep 自己的前綴只答得出「預期的行有沒有出現」，
答不出「有沒有不該出現的行」——函式庫繞過 logger 直接印到 stderr 的那一類，沒有自己的前綴，
只會在反向篩選裡現身。

## 事實怎麼記

每筆事實旁邊要有它的出處：一條本 session 跑過的指令與輸出、原始碼一行、或規格原文引用。
指令要能重跑——把可重現的探測指令收成一節，下一個人（或下一台機器）照著跑得出來。

issue 回報的、或使用者要求修的執行期失敗，本 session 看得到失敗紀錄的（CI log、本機重現的輸出），列進〈事實〉的症狀清單，每條三件：
訊息原文、出處、修前失敗率。CI 上的症狀，訊息原文用本 session 跑的 `gh run view <id> --log-failed`
取；修前失敗率的分母用本 session 跑的 `gh run list`，數該 workflow 在一個寫明的時間窗內、實際跑到
那支測試的全部 run，時間窗要包住清單上每一次失敗，不能只收抽樣。本機重現的，寫同一個指令跑了幾次。
分母數不出來就寫「分母未知」，那就還沒有修前失敗率。其餘的（使用者口頭提供、issue 只有文字描述、本 session 看不到失敗紀錄的），
寫進〈未決事項〉（等誰：重現），同時寫進頭的〈範圍〉〈先出的缺口〉，重現之後才搬進〈事實〉。之後每次重現嘗試都記在那條症狀底下：條件、
次數、失敗幾次。0 次也照記，不寫成「沒重現」或「只有現場驗得到」。

## supersede：舊結論被推翻時

**不重排、不改寫前面的內容。** 舊條目就地加刪除線，後面接一句「被 X 推翻，見〈某節〉／日誌某則」，
新的結論寫在新的位置。讓一句已知為假的話原封留著，跟把它悄悄改掉，都會讓後面讀的人踩到。

```markdown
- ~~<原本以為成立的那句話>~~ → 被 <日期> 的 <什麼證據> 推翻，見〈事實〉／日誌 <該則標題>
```

## 接手一份已經存在的 `PLAN.md`

先讀它，看索引表還有沒有非 ✅ 的列。

- 同一件事的續作 → 就地更新
- 不同的事 → **停下來問**，並給三個選項：先做完舊的／明確丟棄它／指定新的位置。那些未完成的項目
  可能正在另一個 session 或另一個 worktree 進行中，磁碟上的工作樹狀態是唯一的紀錄

**日誌裡的敘述是紀錄不是證據。** 要引用其中的事實往下推之前，重新驗一次——那些話是別輪寫的，
中間可能已經被 supersede，或者當初就沒驗。

## 常見的自我豁免

| 心裡想的 | 為什麼不行 |
|---|---|
| 「這個改動很小，不用拆」 | 判準是檔案數與子系統數，不是感覺 |
| 「完成判準很明顯，不用寫」 | 明顯的話一句話就寫得出來。寫不出來代表範圍還沒收斂 |
| 「先全部寫完再一起測比較快」 | 第一片的 bug 會讓後面每片都建立在錯的東西上，事後分不出是哪片造成的 |
| 「單元測試全過了，實機應該沒問題」 | 兩者問的不是同一個問題。要寫的是「這一層驗不到什麼」 |
| 「前面那句話錯了，我改掉就好」 | 悄悄改掉會讓看過舊版的人拿著錯的結論走。刪除線加指標 |
| 「這個決定我記得住，不用寫進日誌」 | 下一個 session 的你讀不到這一輪的對話 |

## 收尾檢查

每格拿檔案對一次就有答案：

- [ ] 頭在 60 行內；六個欄位都在，沒有內容的寫「無」
- [ ] 〈判準出處〉每列有來源、它回答什麼、版本（SHA 或讀取日期）三項；一份判準檔都沒有時，
      這裡寫的是 prompt／issue／code 這類非檔案出處，不是「見〈事實〉」
- [ ] 索引表每列有狀態；表上每個 `#` 在下面都有同名小節（`CP<n>` 也要），一個不多一個不少
- [ ] 非 `CP` 的小節三個項目符號都在；`CP<n>` 的小節只有〈完成判準〉
- [ ] 索引表每列在 80 個顯示欄寬內（中文字算兩欄），〈做什麼〉那格沒有括號清單
- [ ] 〈動到的檔〉每條標了所屬子系統，沒有一項超過 5 個檔或標出兩個以上子系統
- [ ] 日誌第一則寫了項目給使用者看過的日期——寫完直接開做的話這一則不會存在
- [ ] 每次項目給使用者看過的那則日誌有「規格沒寫到的輸入」清單（或「無」加理由）；每條落在負責那段
      code 的項目的〈怎麼驗〉、寫了餵入的 test 或指令與預期輸出，或落在頭的〈範圍〉的「不做」、
      理由寫了會造成什麼結果
- [ ] 判準檔每條驗收都對到一個 test 名稱或指令與預期輸出；以狀態為條件的驗收畫了「情況 × 驗收」
      表，每格的 test 驗那條驗收的行為，或是點名的「不做」；判定規則被改動、確認或重述的那則日誌，重畫了這張表
- [ ] 每 2–3 項有一列 `CP<n>`
- [ ] 每筆驗證寫了環境、跑了什麼、對端當時的設定、驗不到什麼四件；讀了服務 log 的那筆另有反向篩選的行數與內容
- [ ] 本 session 看得到失敗紀錄的執行期失敗，〈事實〉有症狀清單，每條有訊息原文、出處、修前失敗率
      （分母是時間窗內實際跑到的全部次數，或寫「分母未知」）；看不到失敗紀錄的，在〈未決事項〉與
      頭的〈範圍〉〈先出的缺口〉各有一條
- [ ] 症狀清單每一條，至少被一項的〈完成判準〉以量到的結果點名；診斷段每個被採用的修法、使用者或
      其他人指定的每個修法，實作它的那一項也點名了；這些項目都有診斷段，每筆根因證據旁有
      「若另一個候選成立會看到」那格，或根因標了「未驗:」（只列一個候選的確定性 bug 除外）
- [ ] 標 ✅ 的診斷型項目，修後 0 次失敗且修前失敗率 × 修後次數 ≥ 3；其餘維持 🔨，〈未決事項〉有對應一條
- [ ] 指定修法而根因「未驗:」的，日誌有一則記下回報內容與使用者的決定
- [ ] 症狀清單每一條，被某個 `CP<n>` 以達門檻的數字涵蓋，或寫進頭的〈範圍〉〈先出的缺口〉並附數字與
      根因是否「未驗:」
- [ ] 對端依賴表每一列，至少有一筆驗證說出它當時的設定，或頭的〈範圍〉〈先出的缺口〉指名它沒被涵蓋、
      為什麼可以先出
- [ ] 沒有實機驗證的項目，頭的〈範圍〉〈先出的缺口〉裡指名了是哪些、為什麼可以先出
- [ ] 〈事實〉每筆有出處（指令／`file:line`／規格原文）
- [ ] 未決事項每條有「等誰」
- [ ] 頭的〈進度〉那行的日期與日誌最新一則對得上
