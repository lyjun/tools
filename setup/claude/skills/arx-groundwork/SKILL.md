# arx-groundwork

開工前把「什麼是對的」釘死，寫成一份別人能檢查的檔案。只到動工前，實作過程與驗證紀錄不寫這裡。

## 三條入口

判準是 **issue 有沒有指向規格文件**，不是「有沒有 issue」。

兩個 tracker：規格單與需求單在 `ardge-labs/ardge-project-issues`（規格 md 也在這個 repo），
bug 單在 `ardge-labs/ARX-bug`。跨 repo 的關聯只寫得出完整 URL，`#nnn` 是同 repo 內的。

| 入口 | 外顯訊號 | 判準來源 |
|---|---|---|
| A | issue body 有 `## Specification` 欄，指向 ardge-project-issues 的某份 md | 規格原文 |
| B | issue 由自己開（工作任務），或根本沒有 issue | 沒有外部判準，要自建 |
| C | bug 單，或 issue 有 parent / sub-issue / relation，或 body 寫著關聯的 issue URL 或 `#nnn` | 順關聯回溯，接回 A 或 B |

C 不是獨立路徑，是回溯步驟：bug 要的判準是「壞掉之前應該是什麼樣」，那個答案不在 bug 單裡。
上游是 A 型走 A、B 型走 B，差別只在範圍收窄到 bug 觸及的那幾節。A 與 C 同時命中直接走 A。

關聯要掃三處：sub-issue / parent 欄、relation 欄、body 內文——只看 GitHub 欄位會漏掉寫在內文的。
**bug 單常常三處都是空的**，那時範圍就是自己去 ardge-project-issues 找：`grep -rl <功能名>`。
找不到要在回覆裡明說「沒有規格文件，以下依 code 推算」——「我依 code 算的」單獨不成立，那句話
沒有回答規格存不存在。

## 產出

`<ardge-workspace>/worktree/<issue-slug>/GROUNDWORK.md`——issue folder 的根層，與各 repo 的
worktree 同層，不放進任何一個 repo 裡面。**沒有 issue 時**（B 路徑常有）`<issue-slug>` 用一個
描述任務的短 slug，並在第 1 節的出處欄寫「無 issue」。

獨立成檔是因為這份的更新節奏是規格被改動時才回頭改，與實作期間每個 session 都在長的紀錄不同。
驗證紀錄不寫這裡——它由實作的人在實作當下寫，不屬於開工前的判準。

### A 路徑

**1. 出處** — 四樣都記，缺一樣之後就回溯不了：issue URL、**釘住 SHA 的規格 permalink**、
規格在 repo 內的路徑、納入比對的章節範圍。

permalink 寫成 `https://github.com/ardge-labs/ardge-project-issues/blob/<sha>/<路徑>`，點開就是
比對過的那份文字。issue 的 Specification 欄用的是 `/blob/main/`，指向會動的 branch——同一個連結
明天打開可能是別的內容，所以它不能當出處。SHA 取法
`git -C <ardge-project-issues> log -1 --format=%H -- <規格路徑>`。

章節範圍：**預設就是 issue 指名的章節，不要擴大**。issue 只連整份規格沒指名時，用 `grep -n '^#'`
列出目錄挑出相關的節。兩種情況都要把**沒納入的節與理由**寫進這一格——那份理由是之後判斷「有沒有
漏」的唯一依據。

要納入 issue 沒指名的節，理由只能是「本輪的改動會實際走到這一節」，而且那一節要單獨列出來標明是
額外納入、附上那句理由。寫不出那句就不要納入：範圍擴大會讓第 2 節列出一堆不屬於本單的「Work
Items 沒有」，把真正漏掉的那條淹掉。

2b 跑完後回到這一節補一行「規格疑點：N 則，見 2b」（沒有就寫 0 則）。之後讀這份檔的人通常只讀開頭，
清單在中段，沒這一行就會被漏看。

**2. 差異檢查（雙向）**

把納入範圍的規格章節裡**每一條可驗證的陳述**逐條列出。可驗證的意思是：實作完成後有辦法指著某個
輸出說它符合或不符合。依規格性質，這些陳述可能是欄位與預設值、狀態轉換、API 的請求／回應形狀、
服務之間的呼叫順序、資料結構、錯誤訊息文字、數值範圍或門檻。不要預設它是哪一種。

兩張表，方向相反（表格內容是範例，欄位照實際規格填）：

規格 → Work Items，找漏掉的：

| 規格條目 | Work Items |
|---|---|
| 逐張介面卡片、依介面編號排序 | 有 |
| Interface Mode 開關（Standalone / Link Aggregation） | **沒有** |
| 連線速率的顯示格式與門檻 | 規格未定義 |

Work Items 與討論 → 規格，找沒有依據的：

| 執行中的要求 | 規格依據 |
|---|---|
| 排序：有插線優先於沒插線 | **規格沒有**（PM 口頭，2026-08-31） |

第二張表的來源只有四種寫法：`規格 <章節>` / `<角色> 口頭（日期）` / `既有行為` / `我推的`。
後兩種要進第 3 節。

停止條件：「沒有」與「規格沒有」兩份清單都寫出來，空的算通過，沒產出清單不算。**Work Items 是
規格的有損轉寫**，所以「issue 寫得很細」不能代替讀規格；反方向漏掉的那條，之後會被誤記成「規格
說的」再以那個身分出貨。

**2b. 規格審視** — 第 2 節拿規格去量 Work Items，規格本身被當成對的：一條限制沒有技術上的必要、
代價卻是安全退步或整個功能不能用時，第 2 節照樣打勾，那條限制就以判準的身分出貨。要審的是規格
定義的功能與限制合不合理，互相矛盾只是不合理的一種。讀過規格、列過第 2 節的人已經帶著它的前提，
所以這一步交給一支全新的 agent（Agent 工具開新的，不用 fork、不續問先前的 agent），第 2 節寫完後
跑一次。

給它的只有：納入範圍的規格原文（第 1 節釘住的 SHA 版本，附行號）、規格所在 repo 的路徑與那個 SHA、
下面這段 prompt。不給第 2 節的表、Work Items 與我的結論——給了，回來的會是對那些結論的確認。相鄰
規格由它自己去讀，只進這一步的輸入，不擴大第 1 節的比對範圍。

```
你是要依這份規格實作的資深工程師，問不到寫規格的人。
規格一律用 `git -C <repo> show <SHA>:<路徑>` 讀，不讀工作目錄。這份規格是 <規格路徑>，同目錄是 <規格目錄>。

對下面貼出的原文裡每一條功能定義與限制（「只能」「不支援」「必須」「須」「未設定時」「不開放」「不會」這類），回答：
1. 規格給的理由是什麼（引原文行號；沒寫就寫「未給理由」）
2. 這個限制是技術上非如此不可，還是產品選擇？技術上非如此不可的，指出是哪個技術事實；那個事實依賴
   外部系統（IdP、瀏覽器、CA、協定）的行為而你無法確認，標「待查證」
3. 代價：誰失去什麼（功能、安全、操作步驟）
4. 有沒有代價更小、仍達成同一目的的做法

限制的理由可能寫在別處：從貼出的原文挑出關鍵名詞，用 `git -C <repo> grep -n <詞> <SHA> -- <規格目錄>` 搜這份規格全文與同目錄
（含子目錄）各檔，命中的節讀過再回答。

只回報符合以下條件的條目：第 2 題答「產品選擇」或「待查證」，而且 (a) 代價是安全或資料外洩、或整個
功能無法使用，或 (b) 第 4 題有代價更小的做法。依代價排序，每則附行號與四題的答案。
順帶：同一件事在兩處（同一份或兩份規格）寫法不同時也回報，附兩處行號。

最後附兩份清單：
- 檢視過但不回報的條目，每則一句理由
- grep 了哪些詞、各命中哪些檔哪幾行

沒有要回報的就寫「nothing important left」，兩份清單照附。

<納入範圍的規格原文，附行號>
```

回來的每則先回頭讀那幾行原文核對，不照單收。審查者引用的外部文件，只當線索，不當已驗的事實。
「檢視過但不回報」的每一則也要核對：理由是技術上必要的，回頭讀原文確認它點名的技術事實沒被規格
其他地方反駁，依賴外部系統的先查證；理由是代價不大的，回原文確認代價沒有落在安全或資料外洩、或整個
功能不能用。被反駁、查不到或落在其中的，移進「規格疑點」。然後分堆：

- **規格疑點**：核對後仍成立的回報條目（判定為產品選擇或待查證，或兩處寫法不同），一律歸這堆，
  不得分進另外兩堆——選哪邊、接不接受代價，都不是我能替規格擁有者決定的。寫進本節的〈規格疑點〉清單，
  每則編號（S1、S2…），附規格版本與行號、四題答案、建議做法；依賴外部系統行為的先查證，查不到的標「未驗」，寫明是哪一題依賴哪個外部行為；規格裡重述同一件事的
  其他行（用審查者的 grep 詞再搜一次，規格用到的每種語言各至少一個詞），以及用同一組詞搜 issue body 全文命中的句子，一併列在同一則
- **規格裡已經有答案**：審查者漏讀了規格裡回答這一點的原文，在本節記那段原文的行號。拿來作答的原文若
  與被回報的那行不能同時成立，就是兩處寫法不同，歸〈規格疑點〉，不歸這堆
- **讀錯**：審查者引的原文不是它說的意思，丟掉，在本節記一句讀錯了什麼

本節留下：〈規格疑點〉清單、審查者 grep 的詞與讀了哪些檔、每則的分堆結果、「檢視過但不回報」那份清單。
〈規格疑點〉在這裡不跟使用者討論，只列出來；使用者怎麼回覆、規格擁有者怎麼答覆，記在動工時的計畫裡，
不回寫這份檔案。

**3. 規格未定義的格子** — 每格標歸屬：誰有權決定這件事（PM、另一個 repo 或角色的擁有者、或我
自己定）。沒有歸屬的問題會被塞進錯的地方，例如把一個要 PM 拍板的產品決定寫進 QA 的 bug thread，
那條 thread 上沒有對應動作可做。標「我自己定」是合法的，條件是同列有理由且使用者看過沒反對。

已列進 2b〈規格疑點〉的條目不在這裡談，留給動工時的計畫逐則問使用者。其餘歸屬是使用者的格子，以及
第 2 節裡規格有寫、但讀得出兩種以上做法的條目，動工前用 `x-design-dialogue`
一次談完，答案寫進第 3 節（第 2 節來的條目在第 3 節新增一列），來源寫
`使用者 口頭（日期）` 或 `沿用預設：<理由>，使用者未反對`。談不出答案的格子維持「等使用者決定」，不由我代填。

**4. 驗收條件對應** — issue 的 Acceptance Criteria 逐條，標由誰驗、怎麼驗。

bug 單「問題描述」欄裡的 `[Expect Result]`（以及需求單的 Acceptance Criteria）是**回報者寫的
待驗證宣稱，不是判準**——它跟自己開的 issue 一樣沒有上游權威。最常見
的失效是**拿定義不同的兩個量相比**（例如某個分類加總出來的數字對上硬體標稱容量，中間差著分割表
與 filesystem metadata），對不上會被讀成有缺陷，然後去修一個不存在的東西。所以每條要回答：這個
數字或行為出自規格哪一節，還是回報者自己寫的。

### B 路徑：自建判準

沒有規格時**沒有東西可以拿來 diff**——自己開的 issue，描述事項是由將要實作它的同一個人寫的。所以
不跑差異檢查，改成建立判準本身。一樣記 issue URL，並把描述事項標記為「已知需求，非規格」，否則
下一個 session 會把自己寫的文字讀成上游權威。

1. **術語表** — 每個外部規格名詞一行：它回答什麼問題、值不同的話我的結論會不會變。
2. **地形** — 涉及的 repo 誰產生誰消費、用什麼機制釘版本、現在各自釘在哪個值。
3. **來源對照** — 這份資料在系統上有哪些可能來源，各標「已確認有 / 已確認無 / 未查」。只列得出
   一個來源就是還沒查完，不是「只有一個」；標「未查」的每格附一句為什麼不查。
4. **判準來源** — 每條會影響決定的陳述標「實機取樣 / 規格原文 / 使用者 口頭（日期） / 沿用預設：<理由>，使用者未反對 / 我推論」，
   推論的列成待驗清單。

四格建完之後，即將寫進設計的產品行為、介面形狀、命名、範圍取捨、完成判準各列一行，來源只能是
`使用者 口頭（日期）`、既有 code 的 `file:line`、外部規格原文 `<章節>`，或 `沿用預設：<理由>，使用者未反對`；
寫不出這四種來源的，用 `x-design-dialogue` 談完再動工，談出的答案回填第 4 格。

任務屬於 **per-machine / per-product 查找表**（判準：同一份程式碼要依機種讀不同的值）時，這七格
要在提任何方案之前問過，否則會在寫完欄位定義之後才發現語意要推翻：

1. 顯示字串由誰組（哪一層 repo）
2. 選表的 key 是什麼
3. 表描述「能力」還是「現狀」
4. 對不到表的機種怎麼顯示
5. 已知之後會擴充的維度是什麼
6. 要不要格式版本欄位
7. 嚴格解析能不能進產品路徑

停止條件：七格每格都有使用者的答覆，或標了「沿用預設 + 一句理由」且使用者沒有反對。七格也用
`x-design-dialogue` 問，七格就是那次必問的清單。

## 對端依賴（兩條路徑都要填）

判準是**這個設定的正確行為需不需要另一台機器上的設定配合**。答得出「對端是誰」就要填，
不必先覺得自己不確定。

外顯訊號，不靠自我判斷。三種都算：協定名（802.3ad、LACP、NTP、NFS、iSCSI）；要對面回應
才成立的模式（交握、協商、租約、聚合）；**以及一個列舉值，而它的兄弟值裡有任何一個命中
前兩種**——`balance-rr` 自己不是協定名，但它與 `802.3ad` 同屬 bond mode，所以整組要進表。

一列一個值，三欄——同一個對端會對到多列，因為同組的列舉值全部進表，對端欄重複填同一台
機器。「對端要設什麼」要有出處：規格原文或文件引用，查不到就寫「未查」並附一句為什麼；
對端名稱本身不能因為出處未查而留白：

| 我們寫下的值 | 對端是誰 | 對端要設什麼（出處） |
|---|---|---|
| `<協定名或模式>` | `<哪一台機器 / 哪個服務>` | `<那份規格說對端要做什麼>（<規格檔或 URL>）` |
| `<同組的另一個值>` | `<那台機器 / 服務>` | 未查：`<為什麼還沒查>` |

**沒設時會怎樣不填這裡**——那要量，屬於實作期的驗證紀錄。這張表只回答「有誰、要設什麼」。

## 收尾檢查

每格都是拿產出的檔案對一次就有答案：

- [ ] 第 1 節有釘住 SHA 的規格 permalink，且列了納入與沒納入的章節；額外納入的節各有一句理由；
      A 路徑另有「規格疑點：N 則，見 2b」那一行。
      B 路徑則寫得出已經找過哪些地方而沒有規格
- [ ] 第 2 節的「Work Items 沒有」清單已寫出（空的算通過）
- [ ] 第 2 節的「規格沒有」清單已寫出，每條標了實際來源
- [ ] 2b 有一支全新 agent 的回覆（「nothing important left」也算），附了 grep 的詞與命中檔案——沒附的
      回覆不算；回報的每則都落在三堆之一，「已有答案」附了原文行號、「讀錯」附了一句，〈規格疑點〉每則
      有編號、規格版本與行號、四題答案與建議做法、重述同一件事的其他行、issue body 裡重述的句子與搜過的詞（每種語言各至少一個詞；沒有命中就寫「無」）；「不回報」的每則標了「已核對」或「已移堆」
- [ ] 第 3 節每格都有歸屬；標「我自己定」的同列有理由
- [ ] 第 4 節每條驗收條件標了它的數字出自規格哪一節，或標了「回報者自寫、待驗證」
- [ ] 對端依賴表與術語表（B 路徑）或第 2 節兩張表（A 路徑）逐條對得上：那邊列出的每個
      協定名或模式名，這邊有一列，或在那一條旁邊寫了「不需要對端」並附出處
- [ ] 對端依賴表每列有對端名稱與出處；出處查不到的標「未查」並附理由
- [ ] 每個具體值都指得出一條本 session 跑過的指令與輸出，或句子裡有「示意」二字

最後一格的判準是**這個值不同的話，讀的人會不會照著它行動**——是就要有出處。型號、路徑、容量、
門檻、ID 都算，但清單不是判準，別拿「不在清單上」當豁免。出處只有三種：本 session 量到的、規格
文件的例句、自己編的；後兩種必須在同句寫「示意」或換成量到的值，因為規格的例句被當成量測值出貨
之後，事後看不出差別。

## 常見的自我豁免

這張表比對的對象是**自己剛想好、還沒執行的那個跳過某步驟的理由**。攔截點放在理由本身，不放在
「我覺得不確定的時候」——真正出錯時不會覺得不確定。

| 心裡想的 | 為什麼不行 |
|---|---|
| 「Work Items 寫得很細了，照做就好」 | 它是規格的有損轉寫，漏掉的通常是整個章節而不是一兩條 |
| 「這條需求討論過了，大家都知道」 | 討論過不等於規格有。要進第 2 節第二張表並標實際來源 |
| 「規格是 PM 定的，照做就好」 | 2b 回報的條目，不論有沒有矛盾，接不接受那個代價都是規格擁有者的決定；照做也要先列進〈規格疑點〉讓使用者確認，默默照做就是替擁有者接受了代價 |
| 「2b 我自己讀一遍就好」 | 列過第 2 節的人已經帶著規格的前提，自己讀抓不到自己接受了的那條 |
| 「規格連結就在 issue 裡，之後要看再點」 | 規格在 main 上會動，不釘 SHA 之後讀到的不是同一份文字 |
| 「量到的兩顆都是這樣，所以規則是這樣」 | 樣本不是規則。寫「量到的 N 顆都是」，除非指得出原始碼一行或規格原文 |
| 「這個 mode 不需要對端配合」 | 那是對端行為的結論，不是訊號判定。訊號只看寫下的值是不是協定名／協商模式／它們的兄弟值；判定不需要對端要有出處，寫進第三欄 |

## 邊界

只管開工前建立判準。實作過程、決策紀錄與驗證結果不寫這裡；規格被改動時回來更新第 1 節的
SHA 並重跑第 2 節。
