# 冷讀的執行細節

`SKILL.md`〈Output model〉開頭決定**什麼時候跑**;這份檔是跑的細節。spawn 之前讀完。

## 為什麼有這一步

PR 1333 第二輪的 F2:主張成立(反駁過、fake client 實跑過),作者與同事都沒讀懂,直到同事把 F2 複述錯了才發現。`問題` 欄的逐詞檢查也過了——「volume 想要的份數 N」有定義子句,但「M 與 N 都會被系統自動調整」沒寫出是誰在改,`建議` 也只寫了不能用什麼。缺的不是規則,是有人只拿這段文字讀一次。

同一則的三個版本各冷讀一次:原版第 3 題答不出、第 1 題含糊;更新版第 1–3 題答得出(作者拿到後 20 分鐘推了對的修法);補上與作者前提的對接後四題全過。冷讀還抓到兩處貼出去的行號錯(一處指到別的函式、一處超出檔尾),那兩份使用者都看過——人看稿時不會逐一點開行號。

## 步驟

1. **先寫預期答案。** spawn 之前,每則 `issue` / `question` 自己寫下第 5 步每題的答案,留在內部報告。判定靠它,不靠冷讀者自評「卡住 / 沒卡住」——驗證時 6 段文字有 5 段自評卡住,正例全在其中。
2. **新開 agent。** `general-purpose`,明示 `model: sonnet`。不用 fork:fork 繼承整段對話,就不冷了,而且會丟掉 `model` 參數。一則貼文一支,裡面每則 finding 都由它答。
3. **給它:** PR 參照(`gh pr view <n> -R <o>/<r> --json title,body`)、貼文草稿全文、repo 的絕對路徑與 head ref;2b 再加作者上一則回覆原文。不給內部報告的其他欄位(`程式要求`、`證據`、`根因＋解法`),那些作者拿不到。
4. **讀者設定寫進 prompt:** 它是這份 PR 的作者,懂一般領域(Kubernetes、Longhorn、Prometheus 這類的公開概念)與這個 repo,但沒看過 reviewer 的推理。作答只准用貼文文字,外加打開貼文明確引用的 `file:line`(`git -C <repo> show <head>:<path>`,前後 5 行);不准 grep、trace 其他程式碼,要自己追 code 才答得出的,答「貼文沒寫」。
   - 不准追 code,是因為作者對自己 code 的理解本身可能就是錯的(PR 1333 的作者以為副本數不會變)。讓冷讀者自己追,它會把貼文漏寫的那一步重建出來,原版也會過。
   - 一般領域要放行:驗證時先寫成「不准用背景知識」,結果正例也卡在 StorageClass、Ready 這類作者一定認得的詞上,分不出好壞。
5. **題目,每則各答:**
   1. 哪個值或行為錯了(程式拿哪個值做判斷)
   2. 現有 code 為什麼會這樣:誰、在什麼時候造成
   3. 作者要改成什麼(具體到值或改動)
   4. (僅 2b)作者上一則回覆把什麼當成前提?這則有沒有正面回應它

   另外回報:每個引用的 `file:line` 打開後,是不是貼文說的那個東西。prompt 要寫明「含圖上的節點與箭頭標籤」——圖上的詞沒有地方附說明,最容易漏。
6. **對答案。** 拿它的答案逐題對第 1 步的預期答案:答不出、含糊、或答成別的 → 把那個缺口補進文字,再跑一次;補兩次仍對不上,把差異交給使用者。引用打不開或指錯位置的,直接修正。
7. **之後不再跑冷讀。** 使用者看過、照回饋改完就貼;但改動過的 `file:line`,貼出前自己用 `git -C <repo> show <head>:<path>` 核對一次那行是貼文說的東西(PR 1333 照回饋改寫的那版,行號就從指錯函式改成了超出檔尾)。兩者擋的東西不同:冷讀抓寫的人沒寫出來的(沒點名的值、只有「不能」的修法、指錯的行號),使用者抓寫出來了但不對的(語氣、該不該提、嚴重度)。

## 痕跡

ledger 那行後面加一欄:`冷讀:F2 第 3 題答不出 → 補 2 次後通過;引用修正 1 處`。沒有 `issue` / `question` 時寫 `冷讀:無 issue/question,跳過`。和反駁那欄同理:寫報告的當下就看得到這步有沒有跑過,不必先想起有這個步驟。
